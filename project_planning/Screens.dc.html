S3Configuration — inheritance editor at Pod levelE1.8 · E2.7 · spec §5.1, §5.3

The hardest screen in the product, because the operator has to understand two things at once: what the value is, and where it came from. So every row carries a provenance column and a state marker — inherited rows are quiet, overridden rows are tinted and carry a revert affordance, and secret rows never show a value. Editors are generated from the versioned catalog, so adding a key ships no frontend change.

S5Services onboarding wizard — step 3, verifyE5.12 · spec §16.2, §16.3

This flow replaces an SSH runbook, so it earns a full page rather than a modal. Each service is a self-contained row with its own status, its own last-tested time, and its own retry — one failure never blocks reading the other four. Failures show the actual remedy, because the person who ran the stack is the person reading this. The gate at the bottom is spec §16.5: no provisioning bundle without a verified broker.

S6Provisioning — bundle tracking board (Field Tech)E4.10 · spec §8.5

A board, not a table, because the five provisioning statuses are a pipeline a human physically walks through: cards get written, devices come online, reports get compared. This is also the RBAC-narrowest screen — a Field Tech gets Provisioning and a read-only Map, and the nav shows the rest as locked rather than hiding it. Marking cards flashed is the one bulk action they need, so it is a primary button.
